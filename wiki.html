1. Architettura Jamstack & Modello "Git-as-a-Database"

Il progetto Overrevving è architettato secondo i dettami del paradigma moderno Jamstack (JavaScript, APIs, Markup) con architettura interamente serverless e a costo zero di infrastruttura (Zero-Cost Infrastructure).

A differenza delle applicazioni web tradizionali basate su database relazionali o documentali a pagamento (es. PostgreSQL, MongoDB Atlas, server Node/Django h24), Overrevving implementa il pattern Git-as-a-database:

💾
Storage Nativamento Versionato
Tutti i dati storici, le classifiche, i lap times, i consumi gomme e gli intertempi risiedono come file JSON atomici tracciati su Git. Ogni aggiornamento genera un commit con audit trail completo.
⚡
Distribuzione CDN Globale
GitHub Pages serve i file statici con cache edge globale, tempi di risposta inferiori a 40ms, zero manutenzione di server e immunità a crash da picchi di traffico.
⚙️
Compute On-Demand
I calcoli pesanti (estrazione vettoriale da PDF Dorna, regressione lineare degrado gomme, interpolazione settori) vengono eseguiti su runner Ubuntu effimeri via GitHub Actions.

1. Jamstack Architecture & "Git-as-a-Database" Model

The Overrevving platform is built upon modern Jamstack principles (JavaScript, APIs, Pre-rendered Markup) using a completely serverless, zero-cost cloud architecture.

Unlike traditional monolithic architectures that rely on 24/7 relational/document databases (e.g. AWS RDS, MongoDB Atlas, persistent backend droplets), Overrevving implements the Git-as-a-database pattern:

💾
Native Versioned Storage
All historical results, championship points, lap times, tire degradation stats, and sector splits live as atomic JSON files committed to Git with full audit history.
⚡
Global Edge CDN Delivery
GitHub Pages serves static assets via high-speed edge nodes, delivering sub-40ms latencies worldwide with zero server administration or traffic spike downtime.
⚙️
Ephemeral Compute
Compute-heavy tasks (Dorna vector PDF stream decompression, tire degradation regression, sector interpolation) run on ephemeral GitHub Actions Ubuntu runners.

5. Dati Calcolati & Formule Algoritmiche

Uno dei punti di forza distintivi di Overrevving è che non si limita a riportare i tempi ufficiali, ma applica una serie di algoritmi avanzati di analisi prestazionale e telemetria:

5. Computed Data & Algorithmic Formulations

A core distinctive capability of Overrevving is that it does not merely re-publish raw timing sheets, but computes sophisticated motorsport performance metrics and statistical models:

5.1 Rilevamento Stint, Gomme e Filtro Giri Lanciati (Flying Laps)

Come vengono rilevati gli Stint e le Mescole:

Nel documento Analysis.pdf Dorna, ogni uscita dai box è contrassegnata da Run #N seguita dalle specifiche degli pneumatici slick (es. Slick-Hard Slick-Medium). Il parser estrae:
• Mescola Anteriore (Soft S, Medium M, Hard H).
• Mescola Posteriore (Soft S, Medium M, Hard H).
• Giro di inizio (startLap) e giro di fine (endLap).
• Flag Pit-In (P): rileva se il giro si è concluso con l'ingresso nella corsia box.

Filtro Algoritmico dei Giri Lanciati (Flying Laps):

Durante le prove libere molti giri sono rovinati da traffico, bandiere gialle, prove di partenza o errori di traiettoria. Per calcolare il vero passo di un pilota, i tempi vengono filtrati secondo questa formula:

FORMULA MATEMATICA FILTRAGGIO GIRI LANCIATI
Sia L_valido = { l ∈ Stint | l.pit == False e l.sec < 180.0s }
Sia T_min = min(l.sec per l in L_valido)

Un giro l è considerato "Giro Lanciato Valido" (Flying Lap) se e solo se:
    l.sec ≤ (T_min × 1.15)  [ovvero entro il 115% del miglior tempo dello stint]

Calcolo del Tasso di Degrado Pneumatici (Degradation Rate):

Per ciascuno stint composto da almeno 4 giri lanciati validi, viene calcolata la regressione lineare tra il numero di giri sul pneumatico (x) e il tempo sul giro in secondi (y):
y = m · x + q
La pendenza m rappresenta il delta degrado al giro (espresso in decimi di secondo, es. +0.048s/lap). In base alla pendenza, lo stint viene classificato in:
• Low Wear (m < 0.03s/giro): usura minima, passo costante.
• Medium Wear (0.03s ≤ m ≤ 0.08s/giro): degrado fisiologico controllato.
• High Wear (m > 0.08s/giro): crollo prestazionale gomma.

Stint & Tire Compound Detection:

In Dorna's Analysis.pdf, pit exits are marked by Run #N followed by slick specifications (e.g. Slick-Hard Slick-Medium). The parser extracts:
• Front Tire Compound (Soft S, Medium M, Hard H).
• Rear Tire Compound (Soft S, Medium M, Hard H).
• Start Lap (startLap) and End Lap (endLap).
• Pit-In Flag (P): identifies laps terminating in pit-lane entry.

Flying Lap Algorithmic Filter:

Practice sessions are affected by out-laps, traffic, yellow flags, and practice starts. To isolate representative race simulation laps, times undergo algorithmic filtering:

FLYING LAP FILTER ALGORITHM
Let L_valid = { l ∈ Stint | l.pit == False and l.sec < 180.0s }
Let T_min = min(l.sec for l in L_valid)

A lap l is classified as a "Valid Flying Lap" if and only if:
    l.sec ≤ (T_min × 1.15)  [within 115% of the fastest lap of that run]

Tire Degradation Linear Regression:

For stints containing at least 4 valid flying laps, a least-squares linear regression is computed between tire age in laps (x) and lap time in seconds (y):
y = m · x + q
The slope m yields the degradation delta per lap (e.g. +0.048s/lap), categorized into:
• Low Wear (m < 0.03s/lap): minimal tire wear, highly consistent pace.
• Medium Wear (0.03s ≤ m ≤ 0.08s/lap): normal controlled thermal degradation.
• High Wear (m > 0.08s/lap): significant performance cliff.

5.2 True Pace Range (Violin / Fork) e Densità dei Tempi (Density Mode)

True Pace Range & Variance Fork (Card 5):

Il tempo secco sul giro singolo (PB) non rappresenta il reale potenziale in gara. La Card "True Pace" visualizza la distribuzione statistica di tutti i giri lanciati puliti attraverso una barra a forcella (fork / box-plot whiskers):
• Minimo (PB): il giro più veloce in assoluto registrato nella sessione.
• 25° Percentile (Q1): limite superiore del 25% dei migliori passaggi.
• Mediana (50°): il tempo baricentrico del passo gara effettivo del pilota.
• 75° Percentile (Q3): confine dell'Interquartile Range (IQR = Q3 - Q1).
• Massimo (Whisker Alto): calcolato come Q3 + 1.5 × IQR escludendo outlier anomali.
Una forcella stretta indica una costanza di guida eccezionale; una forcella larga denota instabilità o degrado improvviso.

Lap Time Density & Modal Pace (Card 4):

L'istogramma di densità scompone l'arco temporale in bin da 0.25 secondi. La Modal Pace (Moda del Passo) individua il bin in cui il pilota ha completato il maggior numero di giri, rivelando il vero "ritmo naturale" della moto sulla distanza.

True Pace Range & Variance Fork (Card 5):

Single-lap qualifying benchmarks do not correlate directly with race endurance. The "True Pace" visualization displays statistical dispersion of all clean flying laps via horizontal variance forks (box-whisker style):
• Absolute Minimum (PB): fastest single lap recorded in the session.
• 25th Percentile (Q1): upper boundary of top 25% pace.
• Median (50th Percentile): true center of the rider's competitive pace.
• 75th Percentile (Q3): upper boundary of Interquartile Range (IQR = Q3 - Q1).
• High Whisker Max: clamped at Q3 + 1.5 × IQR to eliminate unrepresentative outliers.
A compact fork signifies supreme mechanical and physical consistency; a wide fork highlights severe pace degradation or instability.

Lap Time Density & Modal Pace (Card 4):

The density histogram divides the time continuum into 0.25-second buckets. The Modal Pace pinpoints the exact time window with the highest frequency of laps, revealing the bike's genuine cruising rhythm.

5.3 Track Sector Analysis (Intertempi T1, T2, T3, T4)

Per ogni sessione analitica (FP1, PR, FP2), Overrevving genera quattro card orizzontali disposte su un'unica riga (.sector-grid-1row), ciascuna dedicata a un settore del tracciato:
• Segmenti di Stint con Gap: all'interno del grafico, ogni stint di giri consecutivi è tracciato affiancato al precedente, con un micro-gap visivo in corrispondenza del rientro ai box (in-lap/out-lap).
• Giro Ideale Teorico (Optimal Lap): calcolato sommando i migliori intertempi assoluti ottenuti in qualsiasi giro:
T_ideal = min(T1) + min(T2) + min(T3) + min(T4)
• Delta sul Best Settore: ogni passaggio nel tooltip mostra l'esatto distacco dal settore record della sessione e la velocità di uscita alla fotocellula (Speed Trap).

For each practice session (FP1, PR, FP2), Overrevving renders four horizontal cards laid out in a single responsive row (.sector-grid-1row), each analyzing one circuit split:
• Stint-Aligned Segments with Gaps: consecutive flying laps within the same run are displayed side-by-side with micro-gaps highlighting pit entries and tire changes.
• Theoretical Optimal Lap: synthesized by summing the single fastest sector times set across all runs:
T_ideal = min(T1) + min(T2) + min(T3) + min(T4)
• Sector Delta Analysis: every hover tooltip reveals the precise gap to the absolute session sector benchmark and top speed trap recordings.

5.4 Ricostruzione del Grafico Posizioni Giro per Giro (Lap Chart)

Nelle gare in cui il documento Dorna LapChart.pdf presenta codifiche non tabulari o interruzioni da bandiera rossa (es. GP Malesia 2026), entra in azione l'algoritmo di simulazione cumulativa temporale (compute_lap_chart_from_sectors):

ALGORITMO RICOSTRUZIONE LAP CHART
1. Per ogni pilota r e per ogni giro l da 1 a L_totale:
   T_cum(r, l) = ∑ (laps[1..l].time in secondi)

2. Per ciascun giro l da 1 a L_totale:
   Ordina tutti i piloti attivi in modo crescente per T_cum(r, l):
   Posizione_Giro(r, l) = indice_ordinamento + 1

3. Genera la struttura JSON:
   "riders": { "Marc Marquez": [1, 1, 2, 2, ...], "Pedro Acosta": [2, 2, 1, 1, ...] }

Il risultato alimenta il grafico Chart.js chart-rac-lapchart con curve ad asse invertito (P1 in alto, P22 in basso).

For races where Dorna's LapChart.pdf lacks clean tabular encoding or undergoes red-flag multi-part restarts (e.g. Malaysia GP 2026), Overrevving engages its cumulative temporal position reconstruction engine (compute_lap_chart_from_sectors):

LAP CHART RECONSTRUCTION ALGORITHM
1. For every active rider r and each lap l from 1 to Total_Laps:
   T_cum(r, l) = ∑ (laps[1..l].time_seconds)

2. At every individual lap index l:
   Sort all active riders in ascending order of cumulative time T_cum(r, l):
   Lap_Position(r, l) = sorted_index + 1

3. Produce Chart.js payload:
   "riders": { "Marc Marquez": [1, 1, 2, 2, ...], "Pedro Acosta": [2, 2, 1, 1, ...] }

This powers the responsive chart-rac-lapchart Chart.js instance with inverted Y-axis (P1 at top, P22 at bottom).

5.5 Sintesi Automatica della Griglia di Partenza da Q1 e Q2

Nei Gran Premi del Motomondiale la griglia non viene pubblicata come singola sessione fino a pochi minuti prima della gara. Lo script update_motogp_sessions.py la calcola automaticamente non appena Q1 e Q2 sono disponibili:
1. Identifica i primi due classificati del Q1 promossi in Q2 (promoted = {Q1[0], Q1[1]}).
2. Assegna le posizioni da P1 a P12 nell'ordine esatto della classifica del Q2.
3. Assegna le posizioni da P13 a seguire ai piloti del Q1 che non sono stati promossi, preservando i rispettivi tempi e gap.
4. Inietta il blocco "grid": [...] in STATIC_EVENT_DATA e crea la card "Starting Grid" con il colore dedicato.

In MotoGP, official starting grids are often delayed until minutes before sprint launch. update_motogp_sessions.py synthesizes the official starting order immediately following Qualifying:
1. Detects the top 2 Q1 finishers promoted to Q2 (promoted = {Q1[0], Q1[1]}).
2. Allocates positions P1 through P12 directly from the Q2 classification.
3. Allocates positions P13 downward from remaining Q1 participants in qualifying rank order.
4. Injects the synthesized "grid": [...] array into STATIC_EVENT_DATA and displays the dedicated "Starting Grid" column.

6.4 Gestione delle Concorrenze & Git Rebase Safety Loop

Poiché più workflow GitHub Actions possono essere eseguiti quasi simultaneamente (es. il workflow notizie orario e il workflow MotoGP ogni 10 minuti), per evitare il fallimento dei push Git con errori di tipo non-fast-forward rejected, ogni job esegue un loop di sicurezza con rebase atomico:

BASH SAFETY PUSH SCRIPT
git config --global user.name 'github-actions[bot]'
git config --global user.email 'github-actions[bot]@users.noreply.github.com'
git add event.html event_moto2.html event_moto3.html category.html motogp.html data/ exports/ js/

if git diff --staged --quiet; then
  echo "Nessuna modifica da inviare."
else
  git commit -m "Auto-update MotoGP results, analysis and sectors [skip ci]"
  git pull --rebase origin main
  git push origin main
fi

Because multiple GitHub Actions workflows may execute concurrently (e.g. hourly news fetching alongside high-frequency 10-minute session updates), standard git pushes could fail with non-fast-forward rejected. To ensure zero-downtime concurrency, all jobs execute a rebase-push safety loop:

8. Normalizzazione Nomi Piloti & Protezione Casi Limite

Le fonti ufficiali riportano spesso i nomi in formati eterogenei o con caratteri speciali (es. VIÑALES, Di Giannantonio, ÖNCÜ, RAZGATLIOGLU). Il sistema applica un algoritmo a doppio livello di normalizzazione:

⚠️
Lezione Imparata (Bug Öncü): In precedenza, un controllo su re.search(r".NC.", u) privo di delimitatori di parola convertiva erroneamente sia Francesco Bagnaia che Franco Morbidelli in Deniz Öncü! La regex è stata corretta con \b[ÖO]NC[ÜU]\b e accompagnata da un filtro anti-corruzione che verifica la coerenza dei piloti rispetto alla categoria di appartenenza.

Regole di Normalizzazione:
• Preservazione rigorosa dei caratteri speciali e accenti: Maverick Viñales, Fabio Di Giannantonio, Deniz Öncü.
• Assegnazione univoca di numero di gara e codice alfanumerico (es. FB63 per Bagnaia #63, MM93 per Marquez #93, MV12 per Viñales #12).
• Supporto per piloti wildcard e collaudatori (Jake Dixon #96, Dani Pedrosa #26, Pol Espargaro #44, Stefan Bradl #6, Cal Crutchlow #35).

8. Rider Name Normalization & Edge-Case Protection

Official timing providers frequently format names inconsistently (e.g. VIÑALES, Di Giannantonio, ÖNCÜ, RAZGATLIOGLU). Overrevving enforces a two-tier normalization pipeline:

⚠️
Case Study (Öncü Collision Bug): Previously, an unanchored regex check re.search(r".NC.", u) inadvertently matched the letters ANCE in Francesco Bagnaia and ANCO in Franco Morbidelli, turning both into Deniz Öncü! This has been resolved with strict word boundaries \b[ÖO]NC[ÜU]\b plus category validation.

Normalization Protocols:
• Strict preservation of official accents: Maverick Viñales, Fabio Di Giannantonio, Deniz Öncü.
• Deterministic code and number mapping (e.g. FB63 for Bagnaia #63, MM93 for Marquez #93, MV12 for Viñales #12).
• Comprehensive wildcard & substitute rider registry (Jake Dixon #96, Dani Pedrosa #26, Pol Espargaro #44, Stefan Bradl #6, Cal Crutchlow #35).
